# Plan: Add .NET 11 (net11.0) and fill .NET 10 (net10.0) targets in the Cortex packages

Date: 2026-11-21 · Agent: lead-developer · Size: large · Base: v3/bug/247@afb0189 · Branch: v3/bug/247

Request: "as we are here, please lets also add support for dotnet 11."

## Goal
Every shipped Cortex library that targets net8.0 or later also builds and packs net11.0 and net10.0 assemblies. The solution builds with the .NET 11 SDK, and Cortex.Tests passes on the .NET 11 runtime with only the known pre-existing failures.
## Context
- Local toolchain: SDK 11.0.100 is the default (`dotnet --version` → 11.0.100); runtimes 8.0.31, 9.0.20, 10.0.12, 11.0.0 are installed. No global.json in the repo or its parent folders.
- 36 projects. 33 shipped libraries target net8.0 or later. The other three are left alone: `src/Cortex.Mediator.SourceGenerator` (netstandard2.0, required for an analyzer), `src/Cortex.Tests` (net8.0) and `tools/Cortex.Mediator.SourceGenerator.Smoke` (net8.0).
- Already on net10.0: Cortex.Mediator, Cortex.Mediator.Behaviors.Transactional, Cortex.Mediator.Scheduling, Cortex.Streams, Cortex.Streams.Mediator. All others stop at net9.0 or net8.0. Cortex.Mediator.Behaviors.FluentValidation uses the short form `net9;net8;net7` (`src/Cortex.Mediator.Behaviors.FluentValidation/Cortex.Mediator.Behaviors.FluentValidation.csproj:4`).
- Only TFM-conditional code is for netstandard (`#if NETSTANDARD…` in Cortex.Mediator, Cortex.States, Cortex.Types; conditional ItemGroups at `src/Cortex.Streams/Cortex.Streams.csproj:55` and `src/Cortex.Streams.Mediator/Cortex.Streams.Mediator.csproj:59`), so net11.0 compiles the same code as net8.0+.
- Direct references to packages that ship inside the framework: `System.Text.Json` 9.0.3 in `src/Cortex.Mediator/Cortex.Mediator.csproj:70` and `src/Cortex.Streams.AzureServiceBus/Cortex.Streams.AzureServiceBus.csproj:56`. On net10.0+ the SDK may report these as NU1510 (unneeded reference).
- CI: `.github/workflows/sdk-release.yml:19-22` installs `dotnet-version: '9.0.x'`. That SDK can't build the existing net10.0 targets either, let alone net11.0.
- Docs: `src/Cortex.Mediator.Scheduling/README.md:27` "The package targets .NET 8, 9 and 10."
- Known pre-existing test failures: Cortex.Streams `SourceOperatorErrorHandlingTests` (2, every run) and the Session/Tumbling window operator tests (some runs).
- Assumption: net11.0 is added on top of each project's existing TFMs. No TFM is removed, and no package version changes unless a net11.0 restore requires it.
## Approach
Prepend `net11.0` to `<TargetFrameworks>` in the 33 shipped libraries, and `net10.0` too in the 28 that lack it (user's Scope answer), keeping their other TFMs. NuGet picks the nearest compatible dependency group for net11.0 (net10/net9/net8/netstandard), so no package bumps are expected. Run Cortex.Tests on both net8.0 and net11.0, so the .NET 11 runtime runs the referenced libraries' net11.0 builds. Any NU1510 that appears only on net11.0 is fixed by limiting that reference to the TFMs that need it, logged as a Ruling. One task per project family so each can be reviewed and reverted alone.
- Rejected: only the 5 projects already on net10.0 — the other 28 would still have no net11.0 build, which isn't "support for dotnet 11".
- Rejected: a global.json pinning SDK 11 — it would force every contributor onto SDK 11; any SDK ≥ 11 already builds net11.0.
## Out of scope
- Removing old TFMs (net6.0, net7.0, netstandard) and bumping packages to their 11.0 versions (issue #247 part 2).
- New features that use .NET 11 APIs.
## Verification
- `dotnet build Cortex.sln -c Release -nologo` → exit 0, "0 Error(s)", no warning that wasn't in the base build (baseline taken before Task 1 with the same SDK).

- `dotnet list Cortex.sln package --vulnerable --include-transitive` → every project "has no vulnerable packages".
- End to end: `dotnet pack src/Cortex.Mediator -c Release --no-build -o sophon-scratch-pack` produces a nupkg with a `lib/net11.0/` folder.

## Risks
- A third-party package may have no asset that net11.0 can use (native packages such as RocksDB and DuckDB are the most likely). Restore would then show NU1701 or a build error; the fix is a Ruling or a question to you.
- NU1510 warnings for framework-provided references (System.Text.Json) on net11.0.
- The connector packages are only compile-checked on net11.0. Cortex.Tests doesn't reference them.
- The release workflow change takes effect only when a PR into `v*/main` merges; it can't be run locally.
